# llm-proxy frontend — дизайн

Дата: 2026-09-22
Статус: согласован, готов к написанию плана реализации
Парный документ: `llm-proxy-backend`, `docs/specs/2026-09-22-llm-proxy-design.md`

---

## 1. Назначение и границы

Веб-интерфейс шлюза. Две роли, один код:

- **Личный кабинет** — выпуск и отзыв API-токенов, собственный расход, готовая инструкция
  подключения.
- **Админка** — пользователи и их доступ к моделям, аккаунты провайдеров, настройки шлюза.

Чат здесь не живёт. Это панель управления доступом, а не клиент к моделям.

**Не входит в MVP:** отображение квот потребления пользователя, командные пространства,
мобильное приложение. Адаптивность до ширины телефона — входит.

---

## 2. Стек и обоснование

| Решение | Почему |
|---|---|
| React + TypeScript | требование проекта; типы обязательны — контракт с бэкендом широкий |
| Vite | dev-сервер с проксированием `/api`, сборка в статику |
| CSS Modules | точное совпадение с существующей системой оформления |
| Своя библиотека компонентов | см. ниже |
| TanStack Query | серверное состояние: кэш, инвалидация, повторные попытки |
| React Router | маршрутизация с разделением по роли |

**UI-кит не подключается.** Готовый кит приносит собственную систему оформления, которую
пришлось бы переопределять под наш набор CSS-переменных — это гарантированный дрейф дизайна
и постоянная борьба со специфичностью. Набор нужных компонентов невелик и перечислим (раздел 4),
поэтому своя реализация дешевле сопровождения переопределений.

**Глобального стора нет.** Серверное состояние держит TanStack Query, клиентское (тема, язык,
открытые модальные окна) — контекст и локальное состояние. Redux в приложении из семи экранов
добавил бы слой без задачи.

## 3. Система оформления

Токены дословно совпадают с существующей страницей-инструкцией — интерфейс обязан выглядеть
её продолжением, а не соседним продуктом.

```css
--bg      фон страницы
--panel   фон карточек и полей
--line    границы
--fg      основной текст
--dim     вторичный текст
--accent  ссылки, активные состояния
--code    фон моноширинных блоков
```

**Четыре темы:** `auto`, `light`, `pink`, `dark`. `auto` следует `prefers-color-scheme`.
**Два языка:** `en`, `ru`. Умолчания при пустом хранилище — язык `en`, тема `auto`.

Выбор хранится в `localStorage` (`lang`, `theme`) и **применяется до первой отрисовки**
коротким скриптом в `<head>`, выставляющим `data-theme` и `data-lang` на `<html>`. Без этого
при каждой загрузке видна вспышка темы по умолчанию. Скрипт обязан пережить отсутствие
`localStorage` (приватный режим) — тогда просто умолчания.

**Отличие от статической страницы осознанное:** там оба языка лежат в разметке и
переключаются правилом CSS, здесь — словари. Для одностраничной инструкции дублирование
разметки дёшево, для приложения с формами, таблицами и сообщениями об ошибках — нет.

Типографика: системный шрифт для текста, моноширинный для токенов, идентификаторов моделей и
примеров кода. Ширина колонки контента ограничена, как на странице-инструкции; таблицы
админки могут занимать всю ширину.

## 4. Библиотека компонентов

Минимальный перечень, покрывающий все экраны:

`Button`, `TextField`, `Select`, `Checkbox`, `Toggle`, `Table`, `Card`, `Badge`, `Modal`,
`Toast`, `Tabs`, `CopyField`, `EmptyState`, `Spinner`, `Chart`.

Требования, общие для всех: управление с клавиатуры, видимый фокус, корректные роли ARIA,
поведение при `prefers-reduced-motion`.

`CopyField` — отдельный компонент, потому что показ секрета встречается трижды (новый токен,
временный пароль, ссылка OAuth) и везде обязан вести себя одинаково: значение
моноширинным, кнопка копирования, явное предупреждение «больше не покажем».

`Chart` — тонкая обёртка над легковесной библиотекой построения графиков. Данные приходят уже
агрегированными с бэкенда; на клиенте расчётов нет.

## 5. Экраны

| Путь | Доступ | Содержание |
|---|---|---|
| `/login` | аноним | форма входа и/или кнопка OIDC — состав определяет ответ `/api/auth/config` |
| `/password` | урезанная сессия | смена временного пароля; единственный доступный экран |
| `/` | пользователь | ключи и собственный расход |
| `/connect` | пользователь | инструкция подключения |
| `/admin/users` | админ | список пользователей, карточка пользователя |
| `/admin/providers` | админ | аккаунты вендоров |
| `/admin/settings` | админ | настройки шлюза, прайс-лист, редактор YAML |

### 5.1 `/login`

Состав экрана **не зашит**: клиент запрашивает `/api/auth/config` и рисует то, что разрешено —
форму, кнопку провайдера или обе. При `disable_login_form` формы нет. Ошибка входа не
различает «нет такого пользователя» и «неверный пароль». При блокировке после серии неудачных
попыток показывается, когда можно повторить.

### 5.2 `/password`

Экран урезанной сессии. Любая попытка перейти в другое место возвращает сюда. Требования к
паролю показаны до отправки, а не только в ответе на ошибку.

### 5.3 `/` — кабинет

**Ключи.** Таблица: ярлык, префикс (`sk-…a1b2`), создан, последнее использование, состояние.
Действия: выпустить, отозвать. Отзыв требует подтверждения и называет ярлык — ошибиться строкой
в таблице слишком легко.

Выпущенный токен показывается **один раз** в модальном окне через `CopyField`, с явным
предупреждением и ссылкой на `/connect`.

Колонка «последнее использование» отвечает на главный вопрос при уборке ключей: каким из них
ещё пользуются. Никогда не использованный ключ помечается явно, а не прочерком.

**Расход.** График потребления по времени с переключателем периода, разбивка по моделям,
суммарные числа. Данные с бэкенда уже агрегированы.

### 5.4 `/connect`

Замена прежней статической страницы-инструкции. Блоки для клиентов с **подставленным токеном**,
если пользователь только что его выпустил, и адресами из ответа сервера. Ни одного адреса в
коде фронтенда.

Если токена нет — вместо значения показывается плейсхолдер и ссылка «выпустить ключ».
Раздел «если не работает» с разбором типичных ответов сервера.

### 5.5 `/admin/users`

**Список:** имя, почта, **тип** (человек или сервис), способ входа, роль, политика,
**последняя активность**, состояние. Фильтр по типу, состоянию и способу входа, поиск.

**Карточка:** данные, редактор политики, ключи пользователя с датами использования, последние
запросы, последние события аудита.

**Редактор политики** — центральный элемент админки:

- правила показаны списком «провайдер + шаблон модели»;
- провайдеры и модели подставляются из каталога, шаблон можно ввести руками;
- рядом со списком — **предпросмотр**: какие модели каталога сейчас покрыты. Это единственный
  способ увидеть разницу между `claude:*` и `claude:claude-sonnet-*` до сохранения;
- при `policy_managed_by = idp` редактор **заблокирован**, с отметкой об источнике прав и
  подсказкой, где менять — иначе администратор будет править поле, которое перезапишется при
  следующем входе пользователя.

Предпросмотр обязан оговаривать, что `*` покрывает и будущие модели: список показывает
сегодняшний каталог, а правило шире списка.

**Создание пользователя** возвращает временный пароль — показывается один раз через
`CopyField`, со сроком годности.

**Сервисные учётные записи** заводятся здесь же, отдельным действием. Отличия в интерфейсе
соответствуют отличиям в модели: пароль не запрашивается и не выдаётся, способ входа не
показывается, а в карточке вместо блока входа — **выпуск токенов от имени этого аккаунта**
(обычный пользователь выпускает их себе сам, за сервис это делает администратор). Редактор
политики работает как у всех и никогда не блокируется отметкой об IdP: у сервисной записи
права всегда локальные.

Тип показывается значком в списке и в карточке. Спутать их в перечне легко, а последствия
разные: у сервисной записи за токеном стоит работающая интеграция, и отзыв гасит её целиком.

### 5.6 `/admin/providers`

Аккаунты вендоров: провайдер, метка, состояние, последняя ошибка, обновлён, квота
(доля израсходованного и момент сброса). Действия: отключить, удалить, обновить принудительно.

**Добавление аккаунта — мастер в три шага**, продиктованный тем, как устроен вход у вендора:

1. выбор провайдера;
2. показ ссылки авторизации (`CopyField`) — человек проходит вход **в своём браузере**;
3. поле для callback-URL, который он получил.

Шаг 3 нужен, потому что вход рассчитан на терминал и локальный колбэк; ручная вставка
избавляет от проброса порта. Незавершённый мастер истекает по таймауту — это показывается
на экране, а не выясняется отказом при отправке.

### 5.7 `/admin/settings`

Формы по разделам настроек, прайс-лист моделей таблицей, редактор сырого YAML как аварийный
люк. Редактор проверяет содержимое на сервере до применения и показывает разницу с текущим
состоянием. Применение настроек — отдельное подтверждаемое действие.

## 6. Контракт с бэкендом

REST под `/api`, JSON, сессия в куке `HttpOnly`. Клиент токенов не хранит и в `localStorage`
не кладёт ничего, кроме темы и языка.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/auth/config` | что показывать на `/login`; вызывается до отрисовки |
| `POST` | `/api/auth/login` | локальный вход |
| `GET` | `/api/auth/oidc/start` | начало входа через провайдера |
| `POST` | `/api/auth/logout` | выход |
| `POST` | `/api/auth/password` | смена пароля |
| `GET` | `/api/me` | профиль, роль, признак урезанной сессии, политика |
| `GET`/`POST` | `/api/me/tokens` | список и выпуск |
| `DELETE` | `/api/me/tokens/{id}` | отзыв |
| `GET` | `/api/me/usage` | агрегаты для графиков |
| `GET` | `/api/connect` | адреса и шаблоны для инструкции |
| `GET`/`POST` | `/api/admin/users` | список и создание |
| `GET`/`PATCH` | `/api/admin/users/{id}` | карточка и правка, включая политику |
| `GET` | `/api/admin/users/{id}/activity` | запросы и события аудита |
| `GET` | `/api/admin/catalog` | каталог провайдеров и моделей для редактора политики |
| `POST` | `/api/admin/policy/preview` | предпросмотр покрытия правил |
| `GET` | `/api/admin/providers` | аккаунты вендоров |
| `POST` | `/api/admin/providers/login/{start,complete}` | мастер добавления |
| `PATCH`/`DELETE` | `/api/admin/providers/{id}` | отключение, удаление |
| `GET`/`PUT` | `/api/admin/settings` | настройки |
| `GET`/`PUT` | `/api/admin/prices` | прайс-лист |

**Ошибки** приходят единым видом: машинный код, текст, опционально поле формы. Текст для
человека формирует клиент по коду — иначе интерфейс окажется одноязычным по вине сервера.

`401` уводит на `/login`. `403` при урезанной сессии уводит на `/password`. Прочие `403`
показываются как отказ, без перенаправления.

## 7. Структура и сборка

```
src/
  app/          маршрутизация, провайдеры, границы ошибок
  shared/       ui/, lib/, i18n/, styles/
  entities/     типы и запросы: user, token, usage, provider, settings
  features/     сценарии: выпуск токена, редактор политики, мастер входа провайдера
  pages/        экраны из раздела 5
```

Зависимости направлены внутрь: `pages` → `features` → `entities` → `shared`. Горизонтальных
импортов между `features` нет.

Сборка отдаёт статику. В разработке Vite проксирует `/api` на бэкенд. Базовый путь и адрес
бэкенда — параметры сборки и рантайма, в коде их нет.

**Нейтральность обязательна:** ни одного имени хоста, домена, realm или группы — репозиторий
предназначен к публикации. Всё приходит с сервера или из параметров сборки.

### Образ и запуск

Весь стек поднимается одним `docker-compose.yml` (он живёт в репозитории бэкенда и описывает
три сервиса: базу, бэкенд и этот фронтенд).

**Финальный слой — alpine-вариант nginx, и это не вкусовщина.** Проверка готовности,
объявленная в `docker-compose.yml` бэкенда, дёргает индексную страницу через `wget`, а он есть
только в BusyBox, то есть в alpine-тегах; на debian-варианте `wget` не установлен, и проба
упадёт закрыто — контейнер никогда не станет healthy. Сменить базу можно, но тогда правится и
проба в compose.

Образ собирается многоступенчато: сборка Vite, затем nginx с готовой статикой — ни исходников,
ни инструментов сборки в финальном слое, процесс не от root. Конфигурация nginx отдаёт статику,
проксирует `/api` на бэкенд по имени сервиса внутри сети compose и возвращает индексную
страницу на неизвестных путях — иначе перезагрузка страницы на любом маршруте, кроме корня,
даст 404.

Адрес бэкенда и базовый путь — параметры рантайма контейнера, а не константы сборки: один и тот
же образ обязан годиться для любого развёртывания. Готовность контейнера проверяется отдачей
индексной страницы.

## 8. Доступность и поведение

- Управление с клавиатуры на всех интерактивных элементах, видимый фокус.
- Контраст проверяется во всех четырёх темах; `pink` — самая рискованная.
- Длительные действия показывают состояние; разрушающие (отзыв, удаление) требуют
  подтверждения с названием объекта.
- Секреты не попадают в историю браузера, в адрес и в сообщения об ошибках.
- Без JavaScript приложение не работает — это принято; страница-заглушка объясняет это.

## 9. Проверка

То же требование, что и на бэкенде: поведение проверяется автоматически, вручную остаётся
только внешний вид. Кликать по экранам ради проверки логики — способ не заметить регрессию.

### Уровни

| Уровень | Что проверяет | Чем |
|---|---|---|
| Компоненты | `CopyField` не показывает значение повторно, `Modal` удерживает фокус, редактор политики не сохраняет пустое правило, разрушающие действия требуют подтверждения | тесты поведения, без сети |
| Сценарии | вход, выпуск и отзыв токена, смена временного пароля, правка политики, мастер добавления провайдера, истечение незавершённого мастера | перехват сетевых запросов на уровне слоя моков |
| Контракт | ответы моков соответствуют схеме бэкенда | типы генерируются из схемы; расхождение ломает сборку |
| Сквозной | обе роли от входа до целевого действия | браузерный прогон против поднятого `docker-compose` с поддельным провайдером |

Сквозной уровень работает потому, что бэкенд умеет подниматься с поддельным исполнителем
провайдера: реальные учётные данные вендора для проверки интерфейса не нужны.

### Отдельно проверяемое

- **Заблокированный редактор политики при `policy_managed_by = idp`** — тихий класс ошибок,
  который иначе обнаружится только в проде.
- **Отсутствие вспышки темы при загрузке** — регрессия возможна от любой правки порядка
  подключения скриптов, поэтому проверяется автоматически, а не на глаз.
- **Секрет показывается один раз** и не остаётся ни в состоянии приложения, ни в адресе.

### Ручное

Внешний вид: все четыре темы (у `pink` самый рискованный контраст), оба языка, ширина
телефона. Это вопрос вкуса и контраста, автоматизировать его дороже, чем посмотреть.

## 10. Риски

| Риск | Что делаем |
|---|---|
| Своя библиотека компонентов растёт в подобие кита | перечень зафиксирован в разделе 4; расширение — осознанное решение |
| Предпросмотр политики вводит в заблуждение насчёт `*` | оговорка в интерфейсе: правило шире сегодняшнего каталога |
| Контракт с бэкендом расходится | типы генерируются из схемы, а не пишутся руками |
| Секрет остаётся на экране дольше, чем нужно | показ один раз, через единый компонент |
